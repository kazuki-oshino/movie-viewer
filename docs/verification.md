## ネイティブでの確認

Shiori Devを別ID・専用の一時保存先で起動した。
動画は自作の90秒H.264 / AAC MP4をコピーして使用。

- 日本語・空白・`#`・`%`を含むパスから登録・表示・再生。
- 約40.767秒のフレームを取得し、メモ・アンバー色・640×360 JPEGを保存。
- 速度メニューの0.1と2.0を操作し、保存JSONでも値を確認。
- 50.767秒・2.0倍速で`⌘ Q`により終了。次の起動でしおり棚と保存位置・速度を復元。
- しおりを押すと約40.767秒へ移動し、再生ボタンが一時停止表示に変化、時刻が進行。
- アプリ終了中に検証動画を移動・改名して再起動。サムネイルとメモは残り、元ファイルの不在を案内。
- 別内容の動画を再指定すると拒否。操作前後のJSONのSHA-256が完全一致。
- 再指定ダイアログのキャンセルでもJSONのSHA-256が完全一致。
- 正しいファイルへの再指定では、動画ID・しおりID・メモ・時刻・色・速度を維持してパスを更新。

### 初期シークの実機回帰確認

最初の実機検証では、再起動・再指定の直後に保存時刻へシークすると、時刻が進む一方で映像が黒くなるケースを検出。
先頭フレームを表示してから再度しおりへ移動すると復帰した。
先頭フレームの読み込みを明示的な0秒シークで開始し、保存位置への移動を`loadeddata`後へ変更した。
修正版を通常版のリリースビルドでも検証。再起動後、40.767秒のしおりへ直接移動して映像付きで再生し、55.433秒の実フレーム・メモ・ブルー色を追加保存できた。
この追加分も640×360のJPEGであることを確認した。
同じ通常版ビルドで動画を再度移動・再指定し、2件のしおり・55.433秒の保存位置・2.0倍速を維持したまま、停止中のフレームも正しく表示できた。
通常版の確認も一時保存先を明示し、個人利用のライブラリは読み書きしていない。

## 再生エラーの診断表示

同日、QuickTimeでは再生できるローカルMP4がShioriではエラーになるとの報告を受け、画面に診断情報を追加した。
問題の動画は受け取らず、個人の動画・ライブラリも読み書きしていない。
再生・初期シーク・保存・ファイル配信の処理は変更していない。原因の特定や修正とは分けた診断用の変更である。

### 読みやすい詳細と共有操作

`make-interfaces-feel-better`の文字・操作領域の指針を適用した。

| Before                                                     | After                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 再生エラーが共通メッセージだけで、動画要素の詳細が失われる | `MediaError.code`と名前、元のメッセージ、読み込み状態、時刻・長さ・映像サイズ・再生状態、URLの方式だけ、登録時サイズ、初期位置の復元状態をエラー発生時に取得して表示。詳細文が空、またはMediaErrorがない場合も明示。                                      |
| 失敗直前の読み込み段階が分からない                         | 最初のイベントからの経過ミリ秒と直近16イベントをメモリ上だけで保持。後続イベントで画面のエラースナップショットは変えず、動画切り替えでリセット。                                                                                                          |
| 共有方法がスクリーンショットや手入力になる                 | 読み取り専用の選択可能な詳細欄と42px高のコピーボタンを追加。コピー拒否・未対応時は詳細を全選択し、手動コピーを案内。既知のファイル名・パス・URLは元メッセージから伏せ、URLエンコード・Unicode表記差も検証。動画タイトル・メモ・画像は診断情報に含めない。 |
| 固定中央配置では詳細が増えると上端・下端へ届かない         | エラー欄内の縦スクロール、長文の折り返し、等幅の詳細欄を追加。短い内容の中央配置は維持し、エラー画面の白いボタンは暗い文字色へ変更。                                                                                                                      |

- 診断情報の単体テスト20件と画面テスト4件を追加。全64件のVitestと23件のRustテストが成功。
- 正常な初期シーク・保存位置の保護、既存のしおり・スキップ・速度の回帰テストも成功。
- ブラウザ検証では、配布対象外の一時ページと動画ではないテキストBlobを使って実際のメディアエラーを発生させた。`MEDIA_ERR_SRC_NOT_SUPPORTED`とブラウザ由来の詳細文を表示し、「詳細をコピー」の成功通知を確認。

## 診断v2：配信ヘッダーとRange応答

Safariでも再生できるという報告を受け、ユーザーの承認後に追加診断と通常版の再ビルドを実施した。
問題の動画そのものは受け取っておらず、原因特定・再生修正が完了したという意味ではない。

### 取得中の案内と、安全に共有できる詳細

`make-interfaces-feel-better`の指針に沿い、既存の操作領域・長文の折り返しを保ち、取得中の状態とコピー可能になるタイミングを揃えた。

| Before                                                 | After                                                                                                                                                                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 診断v1は動画要素の状態のみ                             | `mediaDiagnostics.ts`の識別子をv2に更新。`assetDiagnostics.ts`で同じローカルasset URLのHTTPステータス、Content-Type、Content-Length、Content-Range、Accept-Rangesを取得し、独立したHEAD確認であることを明示。 |
| 配信情報を取得する処理がない                           | HEADのみ3件、先頭・末尾は各2バイトのRange指定。本文取得・GETフォールバック・外部送信は行わず、CSPの接続先だけをローカルassetに限定して追加。標準配信処理とファイルスコープは維持。                            |
| エラー表示後にすぐコピーできる                         | `MediaErrorDetails.tsx`で取得中の案内と`aria-busy`を表示し、コピーは取得完了後に有効化。全体で最大5秒とし、診断失敗時も元のエラーをコピー可能。                                                               |
| 同じセッションの再エラーでスナップショットが置き換わる | `Player.tsx`で最初のエラーを保持し、追加診断は一度だけ実行。動画切り替えで要求を中断し、遅れて届く結果を次の動画に混ぜない。                                                                                  |
| 追加ヘッダーや通信例外の非公開化は対象外               | 選択したヘッダーだけを非公開化して表示。例外文・任意の例外名・応答URL・Content-Dispositionを除外。CORSで見えないヘッダーを「不存在」と区別して表示。                                                          |
| v1のテストと操作説明                                   | 単体テスト20件・画面テスト3件を追加し、READMEと設計資料に診断手順・安全上の制約・Tauri更新時の再検証を追記。                                                                                                  |

### 実行結果

- Vitest 87件、Rust 23件、TypeScript / Vite、Clippy、変更ファイルのPrettier確認が成功。
- タイムアウト時にfetchが中断を無視しても5秒で結果を返すこと、途中キャンセル、遅れて届く例外、HTTP 403 / 404 / 416 / 500、HEADに200が返る場合、外部URLの拒否、パスの非公開化を自動検証。
- 同じmacOSの独立したWKWebViewでも、HEADとHEAD + Rangeに対する200 / 206、およびCORS経由のヘッダー取得を確認。これは標準Tauriそのものの実機検証とは区別した補助確認。
- `npm run app:build`で生成した通常版を、`open --env SHIORI_DATA_DIR=<専用の一時保存先>`で起動。通常の個人ライブラリは読み書きしていない。
- 日本語・空白・`#`・`%`を含む自作の75バイトの非動画MP4を登録し、実際のWebKitエラー4と診断v2を表示。
- 通常HEADは200、Content-Typeは`video/mp4`、Content-Lengthは75。先頭は206 / `bytes 0-1/75`、末尾は206 / `bytes 73-74/75`、両RangeのContent-Lengthは2。3件とも約36msで完了。
- Accept-RangesはCORSで参照できないため`not exposed or absent`と表示。コピー対象の診断文にはファイル名・URL・保存パスが含まれないことを確認。
- 実アプリで「詳細をコピー」の成功通知を確認。続けて正常な自作90秒動画へ切り替え、診断表示が消え、実フレームと再生時刻の進行を確認した。
- `codesign --verify --deep --strict`が成功。問題の動画での追加診断はユーザーによる確認待ち。

[診断v2の実アプリ画面](screenshots/native-player-error-diagnostics-v2.png)を保存した。
