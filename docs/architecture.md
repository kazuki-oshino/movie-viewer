# Shioriの設計

## 目的と範囲

「あの説明が何分だったか」を探す時間を減らすため、ローカル動画の特定時刻にしおりを付ける。
通常の動画管理よりも、複数動画を横断するメモとサムネイルの棚を中心にする。
元動画をコピー・編集せず、必要な記録をアプリ側に持つ。
サーバー、クラウド、アカウントは設けない。

参考アプリKomaの責務分離と独立JSONの保存方式を採用した。
画像の順番と読書位置を扱うKomaに対して、Shioriは動画ID・時刻・メモ・フレーム画像を扱う。
参考アプリのデータや実行ファイルは使用しない。

## 境界

| 層                | 責務                                                         | 扱わないこと             |
| ----------------- | ------------------------------------------------------------ | ------------------------ |
| Reactの機能別画面 | 一覧・動画・メモ・入力と表示                                 | ファイルの書き換え       |
| App               | 遷移前の保存、ダイアログ、終了要求、選択・追加の調整         | 保存形式の検証           |
| application       | 最新状態を保持する直列保存キュー、フレームと時刻の取得       | Rustへの依存             |
| LibraryGateway    | ネイティブ版とブラウザプレビューの差の吸収                   | 画面レイアウト           |
| Tauri             | IPC、ネイティブダイアログ、ウィンドウ、アセットの許可        | メモやハッシュの仕様判断 |
| Rustコア          | 不変条件、内容ハッシュ、JSON、サムネイル、書き込み競合の防止 | WebView、UI状態          |

## 保存モデル

動画にはランダムなUUIDを付ける。
パスはIDではなく「現在のファイルの場所」として保存し、再指定してもIDは変えない。
しおりには別のUUID、秒単位の始点 `seconds`、任意の終点 `endSeconds`、メモ、色、サムネイルIDを保存する。
終点がない（省略またはnull）しおりは地点再生、終点があるしおりはA–Bリピートとして扱う。
区間は0.5秒以上かつ動画の長さ以内とし、Rustでも追加・編集・読み込み時に検証する。
編集時はサムネイルと一致する始点を保持し、種類・終点・メモ・色を変更できる。

保存形式v1の地点しおりとv2の区間しおりを読み込める。読み込みだけではJSONを書き換えない。
新規動画はv3で保存する。旧形式に色調または区間を新たに保存するときにv3へ上げ、バージョンは戻さない。
旧アプリは未知のバージョンを読み込まず警告するため、未知の色調や終点を落とした上書きを防ぐ。
動画としおりは任意の `colorAdjustments`（明るさ・コントラスト・彩度）を持つ。
省略・nullは元の色とし、Rustで明るさ・コントラストの0.5〜2、彩度の0〜2と有限値を検証する。
動画の色調は再生位置と同じ直列保存キューに含め、しおりは作成時の表示色を独立したスナップショットとして保存する。
色調のないしおりを開くと、直前の色を引き継がず元の色に戻す。
時刻は浮動小数の秒を維持し、地点は秒、区間は小数第1位まで表示する。

動画ごとにバージョン付きJSONを保存する。
元動画が見つからなくなっても、保存済みのしおりと画像は表示・編集できる。
表示用の利用可能状態はファイルの状態から都度計算し、保存データに固定しない。
サムネイルのパスはアプリ内のUUIDから構築し、任意のパスを保存先として受け付けない。

### 書き込みと競合

- データフォルダのファイルロックで、別プロセスとの同時利用を拒否する。
- Rustのロック下で最新のJSONを読み、コマンドが担当するフィールドだけを更新する。
- 再生位置の保存で、しおり編集や再指定を上書きしない。
- 再生セッションIDと単調増加するrevisionで、過去のセッションと古い書き込みを拒否する。
- JS側は再生位置の保存を直列化し、待機中の複数更新を最新の1件にまとめる。
- しおり追加はクライアントで発行したUUIDを使う。同じ要求を再試行しても重複を作らない。
- 保存は一時ファイルへ書き込み、ファイルの同期、アトミック置換、親ディレクトリの同期を行う。
- 失敗時は入力を残す。画面の切り替えと通常終了は保存完了を待つ。

ディレクトリ同期の失敗など、書き込みが実際には完了していても応答が失敗する場合がある。
再試行は同じIDを用い、再試行前にメモを編集した場合も最新の内容を保存する。
強制終了やストレージ自体の破損に対するバックアップ機能は含めない。

## 再生とフレーム取得

動画のバイト列をIPCやBase64で転送しない。
Rustが開いた動画の正確なファイルパスだけをTauriのアセットスコープへ許可し、WebKitの`video`要素で再生する。
アセットスコープの初期値は空で、全ディスクを公開する設定は使わない。
サムネイルディレクトリだけは非再帰で許可する。
CSPにより、外部のスクリプト・フォント・画像・動画・フレームの読み込みを許可しない。

Tauri標準のRange応答を利用する。
単一Rangeの応答上限は `vendor/README.md` に記載した変更により8 MiB。Rangeのない要求は全体を読む実装である。
そのため、任意のクライアントに対して常に一定メモリでストリームするサーバーとは位置付けない。
通常の動画要素は`preload="metadata"`を使い、再生・シークに必要な範囲を要求する。

しおり追加時は一時停止してからシーク完了／フレーム読み込みを待つ。
同じ同期処理で時刻を読み、Canvasへフレームを描画する。
長辺640pxのJPEGだけをIPCで送り、Rustでも形式・サイズ・解像度を検証する。
生成できない場合はエラーを表示し、空のサムネイルで保存しない。
動画のカバー画像は補助表示なので、生成失敗で再生そのものを止めない。
区間しおりの作成ではAへ移動してサムネイルを取得する。WebKitは停止状態のシークだけでは黒いフレームを返す場合があるため、無音で再生し、`requestVideoFrameCallback` で映像の準備を確認してから停止・Aへシークする。
待機は6秒で打ち切り、成功・失敗とも停止状態と元のミュート設定へ戻す。

再生開始の要求は初期シーク中も保持し、`seeked`／`canplay`で映像の準備ができてから再生する。
`preload="metadata"`のまま最初に明示的な0秒シークを行い、先頭フレームの読み込みを要求する。
保存位置への初回シークは`loadedmetadata`では行わず、先頭の映像を読み込む`loadeddata`後に行う。
実機で確認した、初期シーク後に音声と時刻だけ進み映像が黒くなる状態を避けるための順序である。
この位置復元が済むまでは再生位置の保存を抑止し、読み込み中の0秒で保存位置を上書きしない。
明示的な一時停止・画面切り替え・しおり作成時には、保留中の再生要求も取り消す。
OSが自動再生を拒否する場合は、時刻を維持したまま再生ボタンの操作を案内する。
ライブラリの読み込み前に終了要求を購読し、初期化エラー画面でも通常終了できるようにする。
遷移前の保存失敗は、移動先の動画が見つからないエラーとは分けて表示する。

### 表示用の色調・拡大・プレビュー

色調は動画要素とサムネイル画像のCSS filterへ適用する。保存用JPEGにはフィルターを焼き込まないため、後の色調編集で劣化や二重適用を起こさない。
拡大は1〜4倍、移動は映像の縦横比と表示領域から限界を計算する。ウィンドウのサイズ変更にも追従し、別の再生セッションでは全体表示へ戻す。
調整パネルは映像に重ね、プレイヤーの高さを縮めない。

タイムラインのプレビューは、ホバーまたはキーボードフォーカス時だけ独立した無音の動画要素を生成する。
150ミリ秒の待機後にシークし、WebKitでは先頭フレームを読み込んでから指定時刻へ移動する。
`requestVideoFrameCallback` で描画されたフレームを待ち、一時停止して表示する。取得待ちは最大6秒とする。
古い要求の完了を破棄し、非表示時は動画ソース・タイマー・フレームコールバックを解放する。
メインの動画要素、再生セッション、再生位置の保存キュー、A–Bリピートには触れない。

### 再生エラーの追加診断

現行は `Shiori playback diagnostics v4`。最初のエラー時点の状態を固定する。
ネイティブ版では同じasset URLへ独立したHEAD要求を3件送り、通常・先頭2バイト・末尾2バイトの応答を最大5秒で確認する。
再生要求そのものとは区別して表示し、応答本文は取得しない。動画の変更時は中断して古い結果を破棄する。
現行v4では例外文、URL、パス、ヘッダーを未加工で記録し、Wryの実リクエスト診断とアプリのstderr末尾もコピー内容に加える。
画面には共有前にファイル名・パスを手動で伏せる案内を表示する。動画・音声の内容は記録しない。
診断の仕様と変更済みTauri / Wryソースの根拠は `vendor/README.md` を正とする。

## ファイル移動と照合

登録と再指定では、全体をBLAKE3で照合する。
パス、ファイル名、更新時刻はハッシュに含めない。
動画の移動・改名は受け入れ、別内容や再エンコードは受け入れない。
読み込み中にサイズや更新時刻が変化した場合は中止する。
ストリーミング計算で、動画全体をメモリに載せない。

通常の再オープンはサイズと更新時刻の比較を先に行う。
異なる場合は全体照合し、一致すれば時刻情報を更新して開く。
同じサイズ・更新時刻を意図的に保った改変、再生中の外部変更、ネットワークドライブの切断を常時監視する機能はない。

## 削除

削除対象のパスはUUIDからアプリ専用フォルダ内に組み立てる。
動画の`path`フィールドを削除APIに渡すことはない。
削除対象がディレクトリでも再帰削除せず、メタデータのシンボリックリンクもリンク先は削除しない。
サムネイル整理は、全ての正常な記録から参照されていないUUID名のJPEGだけを対象にする。
1件でも記録を読み取れない場合、復旧可能性を優先して整理を行わない。

## 検証の分離

ブラウザプレビューは明示操作で追加するメモリ上のサンプルだけを使う。
デモの結果をネイティブ保存の証拠と混同しない。
Rustのコアテストは生成したダミーファイルと実JPEGを一時フォルダに作る。
ネイティブ操作には別IDのShiori Devと、その実行専用のデータフォルダ・動画コピーを用いる。
最終的な確認範囲は[検証記録](verification.md)に記載する。
